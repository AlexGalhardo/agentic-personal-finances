# H10 Identity / Telegram → core

| Field      | Value                           |
| ---------- | ------------------------------- |
| PLAN tasks | Identity / telegram → core      |
| Status     | Done                            |
| Depends on | H08; H09 optional (no hard dep) |
| Risk       | Medium: account deletion + link |

## 1. Goal

Move user-profile, account-deletion policy, and Telegram chat-link rules into
`packages/core` ports/use cases. Keep **better-auth** entirely in the backend
adapter ring (sessions, OAuth, 2FA, API keys).

## 2. Non-goals

- Do not reimplement better-auth in core.
- Do not change Telegram link UX or token TTL semantics (15 minutes).
- Do not change deletion grace days (30) without documenting it.
- Stack upgrades (M\*) out of scope.

## 3. Current state

- `user.service.ts`: profile DTO, `requestDeletion` (blocks active plan),
  `purgePendingDeletions`.
- `telegram.service.ts`: find/link/unlink chat, create/complete link token
  (atomic delete-first redemption).
- Bot imports telegram helpers + `userRepository` paths from backend.
- ADR 0003: linking requires authentication.

## 4. Design

### Ports

```typescript
interface UserProfileStore {
  getById(userId: string): Promise<Result<UserProfile, AppFailure>>;
  updateProfile(
    userId: string,
    patch: { name?: string; image?: string },
  ): Promise<Result<UserProfile, AppFailure>>;
  setTelegramChatId(
    userId: string,
    chatId: string | null,
  ): Promise<Result<void, AppFailure>>;
  findByTelegramChatId(
    chatId: string,
  ): Promise<Result<UserProfile | null, AppFailure>>;
  requestDeletion(userId: string, at: Date): Promise<Result<void, AppFailure>>;
  purgeDeletionsRequestedBefore(
    cutoff: Date,
  ): Promise<Result<number, AppFailure>>;
}

interface TelegramLinkTokenStore {
  create(
    chatId: string,
    token: string,
    expiresAt: Date,
  ): Promise<Result<void, AppFailure>>;
  /** Atomic consume: delete row; return null if missing. Caller checks expiry. */
  consume(
    token: string,
  ): Promise<Result<{ chatId: string; expiresAt: Date } | null, AppFailure>>;
}
```

`UserProfile` includes `plan` / `planExpiresAt` (or `planStatus` mapped) so
deletion can call `hasActivePlan` from core.

### Use cases

| Use case                                       | Behavior                                          |
| ---------------------------------------------- | ------------------------------------------------- |
| `getUserProfile` / `updateUserProfile`         | store only                                        |
| `requestAccountDeletion`                       | `conflict` if `hasActivePlan`                     |
| `purgePendingAccountDeletions`                 | grace days via deps constant                      |
| `resolveUserIdByChat`                          | null ok                                           |
| `linkTelegramChat`                             | `conflict` if chat owned by other user            |
| `unlinkTelegramChat` / `unlinkTelegramForUser` | idempotent                                        |
| `createTelegramLinkToken`                      | random via deps; TTL 15m                          |
| `completeTelegramLink`                         | consume → link; invalid/expired → `invalid_input` |

DTO encryption (`autoGeneratedPassword`) stays in backend `toUserDTO`.

## 6. Implementation steps

1. Ports + use cases with fakes (cover conflict, expiry, active-plan block).
2. Prisma adapters; thin services.
3. Bot: call core use cases (in-process) instead of throwing service classes
   where practical; map `AppFailure` → existing bot errors.
4. Evidence + docs.

## 7. Acceptance criteria

- **AC-1** `requestAccountDeletion` with active plan → `conflict`.
- **AC-2** `completeTelegramLink` expired/missing token → `invalid_input`.
- **AC-3** `linkTelegramChat` other owner → `conflict`.
- **AC-4** Concurrent complete: only one succeeds (adapter delete-first).
- **AC-5** Backend user/telegram unit tests green; `check:deps` green.
