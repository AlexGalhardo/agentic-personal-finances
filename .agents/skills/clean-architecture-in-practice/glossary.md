# Glossary: Clean Architecture in Practice (Lemos, 2022)

**Active Record**: a persistence pattern in which entities carry their own database operations. It is impossible on CA entities, but acceptable on DTOs or data structures (Ch 9)
**Adapter**: converts one technology's calls or data into a port's calls or data (Ch 3, Ch 8)
**Anemic model**: an entity with data and no behaviour. Avoid it (Ch 6)
**Application business rules**: rules about how the system automates the domain. These are the use cases (Ch 2, Ch 7)
**Architecture (essential definition)**: the shape of a system: its division into components, their arrangement and their communication. Architecture = design (Ch 2)
**BCE**: Boundary, Control, Entity (Jacobson), a use-case-driven class structure (Ch 3)
**Bounded Context**: a DDD slice. Each context can contain its own small clean architecture (Ch 3)
**Composition root / Main**: the outermost layer that wires concretions to abstractions and starts the system (Ch 3, Ch 10)
**Component**: a set of modules (Ch 2)
**Controller**: an adapter that unpacks a request, calls one use case and maps the result to a response (Ch 8)
**Dance of the entities**: use cases instantiating entities and calling their rules to reach a goal (Ch 3, Ch 7)
**Data mapper**: transforms storage rows into program data structures. It is the honest name for what ORMs do (Ch 9)
**DCI**: Data, Context, Interaction (Reenskaug & Coplien). Data is the domain, Interaction is the use cases and Context is the runtime roles (Ch 3)
**Dependency Inversion**: high-level policy and low-level detail both depend on an abstraction owned by the high level (Ch 2, Ch 7)
**Dependency Rule**: source dependencies point only inward. Inner code never names outer declarations, including data structures (Ch 3)
**Domain business rules**: critical policies that would exist without software (Ch 2, Ch 6)
**DTO (UserData, NoteData)**: a plain data structure that crosses layers so that entities never leave the core (Ch 7)
**Either**: a return type holding an error (Left) or a success (Right), used for expected failures (Ch 4)
**Entity**: critical business data plus critical business rules (Ch 2, Ch 6)
**Factory (main)**: a function that builds a configured concretion, such as `makeUserRepository` (Ch 10)
**Factory method (domain)**: a validating static `create` that is the only constructor path (Ch 6)
**Frameworks & Drivers**: the outermost technical layer, consisting of glue code to libraries (Ch 3, Ch 9)
**Glue code**: code whose sole job is adapting a library to a port (Ch 9)
**Hexagonal Architecture / Ports & Adapters**: the core talks to the world through ports, and adapters fit specific technologies to them (Ch 3)
**Humble Object**: split hard-to-test code (the view) from testable logic (the presenter) (Ch 3)
**Interactor**: Martin's term for a use-case object (Ch 3)
**Interface Adapters**: the layer converting data between use cases and external formats. It holds MVC and the controllers (Ch 3, Ch 8)
**Lead time**: the time from a problem to a delivered solution. Minimize it sustainably (Ch 2)
**Middleware**: logic run before an operation. Here it authenticates and authorizes requests (Ch 8)
**Module**: an aggregate of functions and data (a class, or a source file) (Ch 2)
**Pluggable architecture**: the core at the centre, with details as swappable plug-ins (Ch 2)
**Port**: an interface owned by an inner layer and implemented or called by an outer one (Ch 3, Ch 7)
**Presenter**: formats application data for display, so that the view stays humble (Ch 3)
**Primitive obsession**: a code smell of raw primitives where a Value Object belongs (Ch 6)
**Repository**: a persistence port per aggregate. It is simplified here compared with Fowler and Evans (Ch 7, Ch 9)
**Screaming Architecture**: structure that announces the use cases, not the framework (Ch 2)
**shared folder**: stable cross-layer utilities (such as Either). It is not a layer (Ch 4)
**Simple, not simplistic**: the balance between over-engineering and under-structuring (Ch 11)
**Structure vs infrastructure**: design of components and modules vs the supporting technologies (Ch 2)
**Stub**: a fake port implementation used for isolated tests (Ch 7)
**Unit of Work**: tracks the changes in one business transaction and commits them together (Ch 9)
**Use case**: a high-level operation performed by an actor. It holds the application rules (Ch 3, Ch 7)
**Value Object**: an immutable, value-equal, self-validating small object (Email, Password, Title) (Ch 6)
**Walking Skeleton**: a minimal end-to-end feature built on all the chosen technologies, early in a project (Ch 5)
